**2.1. Для чого потрібні AMIs? Чим відрізняються приватні та публічні AMIs?** <br>
**AMI (Amazon Machine Image / Машинний образ Amazon)** — це стандартизований незмінний шаблон віртуального диска, який інкапсулює встановлену операційну систему, системні бібліотеки, попередньо інстальоване прикладне програмне забезпечення та базову конфігурацію, необхідну для ініціалізації та старту інстансу Amazon EC2. AMI виступає фундаментальною основою моделі IaaS, забезпечуючи швидке та повторюване клонування однотипних серверів.
*   **Публічні AMIs (Public AMIs):** загальнодоступні базові образи, які офіційно верифікуються та підтримуються інженерами AWS (наприклад, актуальні релізи Ubuntu Server, Amazon Linux 2023, Debian, Red Hat Enterprise Linux, Windows Server), або комерційні образи від сторонніх вендорів, розміщені у каталозі **AWS Marketplace** із готовим набором серверного ПЗ (WordPress, GitLab, Nginx Plus тощо).
*   **Приватні AMIs (Private AMIs):** спеціалізовані користувацькі образи (Golden Images), створені безпосередньо розробником або системним адміністратором на основі вже налаштованого робочого інстансу. Вони є закритими для зовнішнього світу, зберігаються в межах облікового запису та можуть контрольовано надаватися для використання іншим акаунтам у межах корпоративної організації AWS Organizations.

--------------------------------------------------------------------------------

**2.2. Для чого потрібні EBS? Які типи EBS підтримуються в AWS?** <br>
**Amazon EBS (Elastic Block Store)** — це сервіс надання блокових дискових сховищ високої доступності, що монтуються до віртуальних машин EC2 аналогічно фізичним накопичувачам (SSD або HDD). Головною перевагою EBS є його персистентність: збережені дані не залежать від життєвого циклу самої віртуальної машини й не втрачаються під час її зупинки чи перезапуску сервера. Блоки диска автоматично реплікуються всередині зони доступності (AZ) для захисту від апаратних відмов.

**Класифікація та типи підтримуваних дисків EBS:**
1.  **General Purpose SSD (gp2 / gp3):** універсальні твердотільні накопичувачі на флешпам'яті з оптимальним балансом вартості та швидкодії. Сучасний стандарт **gp3** дозволяє незалежно конфігурувати базову пропускну здатність (Throughput до 1000 МБ/с) та кількість операцій вводу/виводу (IOPS до 16 000) без обов'язкового збільшення фізичного розміру тому. Застосовуються для системних розділів ОС, середовищ розробки та вебсерверів.
2.  **Provisioned IOPS SSD (io1 / io2 / io2 Block Express):** преміальні накопичувачі з екстремальною продуктивністю та мінімальною затримкою sub-millisecond. Забезпечують гарантовану пропускну здатність до 256 000 IOPS та коефіцієнт надійності 99.999% (Durability). Призначені для критично важливих реляційних СУБД (Oracle, Microsoft SQL Server, PostgreSQL, SAP HANA).
3.  **Throughput Optimized HDD (st1):** недорогі магнітні накопичувачі, оптимізовані для високої пропускної здатності при послідовному зчитуванні/запису великих масивів інформації. Використовуються для систем аналітики великих даних (Big Data, Apache Kafka, кластери Hadoop, обробка потокових логів).
4.  **Cold HDD (sc1):** найбільш економічні дискові томи для великих обсягів рідко запитуваних холодних даних, де швидкість доступу не є критичним фактором.

**2.3. Для чого використовуються Snapshots?** <br>
**EBS Snapshots** — це механізм створення точкових миттєвих знімків (Point-in-Time Backups) блокових накопичувачів EBS, які автоматично стискаються та зберігаються в надійному об'єктному сховищі Amazon S3 (зі стійкістю 99.999999999%).
*   **Інкрементний принцип роботи:** перший створений снапшот є повною копією зайнятого дискового простору, тоді як усі наступні зберігають лише ті блоки даних, що змінилися з моменту попереднього копіювання, мінімізуючи витрати на зберігання.
*   **Сфери практичного застосування:**
    *   Регулярне резервне копіювання корпоративних баз даних та файлових систем;
    *   Аварійне відновлення інфраструктури (Disaster Recovery) після збоїв або програмних помилок;
    *   Створення нових дисків та масштабування їх розміру;
    *   Генерація власних приватних образів AMIs для тиражування серверів;
    *   Міграція дискових томів між різними зонами доступності (AZ) та географічними регіонами AWS.

**2.4. Перерахуйте які основні типи інстансів є в AWS? Коли доцільно використовувати кожен з них?** <br>
AWS пропонує велику матрицю віртуальних машин EC2, розділену на спеціалізовані родини під різні профілі робочих навантажень:
*   **General Purpose (Загального призначення — t3, t4g, m5, m6i):** гармонійно поєднують обчислювальну потужність процесора, обсяг RAM та пропускну здатність мережі. Інстанси серії `t` підтримують технологію Burstable Performance (накопичення кредитів CPU для короткочасних пікових навантажень). Оптимальні для хостингу вебсайтів, мікросервісних бекендів, репозиторіїв коду та тестових середовищ.
*   **Compute Optimized (Оптимізовані за обчисленнями — c5, c6g, c7g):** мають найвище співвідношення ядер CPU до обсягу пам'яті та базуються на високочастотних процесорах Intel Xeon, AMD EPYC або енергоефективних чипах ARM Graviton. Доцільні для високонавантажених вебсерверів, наукових математичних розрахунків, кодування потокового відео, пакетної обробки даних та ігрових серверів.
*   **Memory Optimized (Оптимізовані за пам'яттю — r5, r6g, x2gd):** пропонують великі обсяги оперативної пам'яті (до кількох терабайтів) з розрахунку на одне процесорне ядро. Використовуються для In-Memory кешування (Redis, Memcached), пам'яттєвих баз даних, важких систем аналітики в реальному часі та систем класу ERP/CRM.
*   **Storage Optimized (Оптимізовані за сховищем — i3, i4i, d2, d3):** містять інтегровані низькорівневі надшвидкісні диски NVMe SSD з прямим апаратним підключенням. Призначені для високонавантажених сховищ NoSQL (Apache Cassandra, ScyllaDB, MongoDB), розподілених файлових систем та сховищ даних Data Warehousing.
*   **Accelerated Computing (Прискорені обчислення — g4dn, g5, p4de, p5):** оснащені спеціалізованими апаратними графічними прискорювачами (GPU NVIDIA Tensor Core) або процесорами AWS Trainium/Inferentia. Необхідні для тренування й інференсу великих мовних моделей штучного інтелекту (LLM), глибокого машинного навчання (AI/ML), комп'ютерного зору, 3D-рендерингу та складної молекулярної динаміки.

##### Практичне завдання №1: Розгортання та налаштування віртуальної машини GNU/Linux

**<span>2. Перейдіть до сервісу EC2 та оберіть “Launch Instances” для створення нової віртуальної машини на базі ОС GNU/Linux. Відпрацюйте приклад з навчального відео з деякими уточненнями:</span>**
*   **Задайте ім'я нової віртуальної машини “Linux_ПІБ учасників_вашої_команди”**
*   **Оберіть будь-який дистрибутив на базі ОС GNU/Linux, доступний в безкоштовному тарифі**
*   **Оберіть тип інстансу “t2.micro” (або t3.micro)**
*   **Створіть новий SSH-ключ**
*   **Мережеві з'єднання залишаємо за замовчуванням, дозволяємо підключення за протоколами ssh / http / https**
*   **Обираємо розмір диска 8 ГБайтів**
*   **В налаштуваннях User Data як у прикладі додайте команди для встановлення вебсерверу Nginx**
*   **Після завершення конфігурації натиснути “Launch instance” та перегляньте інформацію про його стан**
*   **Перейдіть за ІР-адресою, перевірте, що у Вас дійсно запущений вебсервер Nginx.**

У сервісі Amazon EC2 я натиснув кнопку **Launch Instances** та виконав послідовне конфігурування параметрів віртуального сервера:
1.  **Ім'я сервера:** присвоїв інстансу найменування `Linux_DimaLobatenko`.
2.  **Вибір образу ОС (AMI):** вибрав офіційний дистрибутив **Ubuntu Server 24.04 LTS (HVM)**, позначений плашкою *Free tier eligible* (64-bit x86).
3.  **Тип інстансу (Instance Type):** вибрав конфігурацію **t3.micro** (1 vCPU, 1 GiB RAM), оскільки в багатьох сучасних європейських зонах доступності AWS архітектура `t3` (на базі системи AWS Nitro) замінила серію `t2`, пропонуючи вищу базову стабільність і також входячи до лімітів Free Tier.
4.  **Автентифікація (Key Pair):** згенерував нову криптографічну пару ключів `linux_key.pem` (тип шифрування RSA, формат файлу `.pem` для підключення через SSH). Приватний ключ було збережено на локальному комп'ютері.
5.  **Мережеві правила (Network Settings):** залишив VPC за замовчуванням із публічною підмережею (Auto-assign public IP: Enable). У налаштуваннях брандмауера **Security Group** активував дозвіл вхідного трафіку з інтернету (`0.0.0.0/0`) за трьома портами:
    *   **SSH (порт 22)** — для термінального адміністрування;
    *   **HTTP (порт 80)** — для доступу до вебсервера;
    *   **HTTPS (порт 443)** — для захищеного вебтрафіку.
6.  **Дисковий простір (Storage):** виділив стандартний системний накопичувач обсягом **8 GiB** сучасного стандарту **General Purpose SSD (gp3)**.
7.  **Автоматизація ініціалізації (User Data):** у розділі **Advanced Details -> User Data** розмістив shell-скрипт хмарної ініціалізації `cloud-init`, який виконується root-користувачем при першому завантаженні системи та автоматично встановлює й запускає вебсервер Nginx:

```bash
#!/bin/bash
sudo apt update -y
sudo apt install nginx -yq
sudo systemctl enable nginx
sudo systemctl start nginx
```

##### Відповіді на контрольні питання

**<span>1. Яку роль відіграє Key Pair при підключенні до EC2-інстансу?</span>** <br>
**Key Pair (пара криптографічних ключів)** є ключовим інструментом автентифікації та захисту підключення до віртуальних машин Amazon EC2, побудованим на принципах асиметричного шифрування (алгоритми RSA або ED25519). Пара складається з двох компонентів:
*   **Публічний ключ (Public Key):** автоматично впроваджується інфраструктурою AWS в образ інстансу під час його створення. У системах Linux він записується у службовий файл `~/.ssh/authorized_keys` цільового користувача, а у Windows Server застосовується для криптографічного шифрування початкового випадково згенерованого системного пароля адміністратора.
*   **Приватний ключ (Private Key):** генерується у форматі файлу `.pem` (для OpenSSH) або `.ppk` (для утиліти PuTTY) і завантажується виключно користувачем на його робочий комп'ютер. AWS принципово не зберігає закритий ключ у своїй системі.
*   **Функціональне призначення:** 
    *   *Для серверів Linux:* приватний ключ підтверджує автентичність клієнта під час SSH-хендшейку, що повністю усуває ризики брутфорсу або витоку статичних паролів через незахищені канали;
    *   *Для серверів Windows:* закритий ключ необхідний для локального розшифрування початкового пароля облікового запису `Administrator` у консолі AWS, що гарантує безпечну передачу облікових даних першого входу.

--------------------------------------------------------------------------------

**<span>2. Яка команда використовується для підключення до EC2-інстансу через SSH?</span>** <br>
Стандартна команда у терміналі UNIX-подібних ОС (Linux, macOS) та терміналі PowerShell у Windows має наступний формат:
```bash
ssh -i "шлях/до/приватного_ключа.pem" ім'я_користувача@публічна_IP_адреса
```
*   **Розшифровка параметрів:**
    *   `-i` *(identity file)* — ключ, що вказує шлях до закритого файлу сертифіката `.pem`;
    *   `ім'я_користувача` — стандартний логін гостьової ОС (для Ubuntu — `ubuntu`, для Amazon Linux — `ec2-user`, для Debian — `admin`, для CentOs — `centos`);
    *   `публічна_IP_адреса` — дійсний Public IPv4 хоста або публічне DNS-ім'я інстансу.
*   *Практичний приклад:*
    ```bash
    chmod 400 linux_key.pem
    ssh -i "linux_key.pem" ubuntu@13.61.10.120
    ```
    *(Примітка: команда `chmod 400` є обов'язковою в середовищі Linux/macOS, оскільки клієнт OpenSSH блокує спробу підключення з ключем, відкритим для читання іншим користувачам операційної системи).*

--------------------------------------------------------------------------------

**<span>3. Як можна підключитися до Linux-інстансу AWS EC2?</span>** <br>
1.  **Класичний SSH-клієнт у локальному терміналі:** використання стандартних утиліт OpenSSH, PuTTY, MobaXterm або Termius із авторизацією через локальний файл приватного ключа `.pem`/`.ppk` через відкритий порт 22.
2.  **EC2 Instance Connect:** браузерне підключення з консолі AWS Management Console. Сервіс генерує короткоживучий відкритий ключ, передає його на віртуальну машину через API AWS на 60 секунд і відкриває повноцінний емулятор терміналу без необхідності ручного завантаження `.pem` ключа на клієнтський ПК.
3.  **AWS Systems Manager (Session Manager):** корпоративний підхід до захищеного віддаленого доступу. З'єднання встановлюється за допомогою фонового агента SSM Agent без відкриття порту 22 у брандмауері Security Group і навіть без наявності публічної IP-адреси у сервера.
4.  **EC2 Serial Console:** апаратний текстовий доступ до віртуального послідовного COM-порту інстансу. Використовується для аварійного відновлення доступу, діагностики ядрових помилок (Kernel Panic) та відновлення мережевих конфігурацій при збоях ОС.

--------------------------------------------------------------------------------

**<span>4. Як можна підключитися до Windows-інстансу AWS EC2?</span>** <br>
1.  **Remote Desktop Protocol (RDP):** підключення до графічного інтерфейсу робочого столу за допомогою системної утиліти Windows «Підключення до віддаленого робочого столу» (`mstsc.exe`), Microsoft Remote Desktop для macOS або Remmina/FreeRDP для Linux через відкритий порт 3389. Попередньо виконується дешифрування системного пароля `Administrator` за допомогою пари ключів `.pem`.
2.  **AWS Systems Manager Fleet Manager:** інтегрований у консоль AWS засіб керування вузлами, який дозволяє відкривати повноцінний графічний сеанс RDP безпосередньо у вікні браузера без необхідності відкривати порт 3389 для зовнішнього інтернету.
3.  **Windows PowerShell Remoting (WinRM):** віддалене консольне керування операційною системою через протокол WS-Management (порти 5985 для HTTP або 5986 для HTTPS), що дозволяє автоматизувати конфігурування сервера та виконання сценаріїв PowerShell без завантаження важкої графічної оболонки.

--------------------------------------------------------------------------------

**<span>5. У чому відмінність між станами Stop і Terminate для EC2-інстансу?</span>** <br>

| Критерій порівняння | **Стан зупинки (Stop)** | **Стан видалення (Terminate)** |
| :--- | :--- | :--- |
| **Обчислювальні ресурси (vCPU, RAM)** | Повністю вивільняються з фізичного сервера-хоста AWS. | Повністю вивільняються з фізичного сервера-хоста AWS. |
| **Системний накопичувач (EBS Volume)** | Зберігається в поточному стані з усіма файлами, конфігураціями та системними змінами. | За замовчуванням повністю знищується (якщо активна опція `DeleteOnTermination`). |
| **Публічна IP-адреса (Public IP)** | Автоматично звільняється (якщо не використовується постійна Elastic IP); при новому старті призначається нова адреса. | Назавжди втрачається та повертається до пулу адрес AWS. |
| **Можливість відновлення/старту** | Інстанс можна запустити повторно (**Start**) у будь-який час зі збереженням структури системи. | Безповоротне знищення: інстанс неможливо відновити чи запустити знову. |
| **Тарифікація та білінг (Billing)** | Плата за обчислювальні години EC2 **зупиняється**; нараховується лише мінімальна вартість за зберігання диска EBS. | Будь-яка тарифікація за інстанс та прив'язані накопичувачі **повністю припиняється**. |

##### Висновки
У ході виконання лабораторної роботи було практично досліджено базову обчислювальну інфраструктуру IaaS хмарної платформи Amazon Web Services на прикладі сервісу Amazon Elastic Compute Cloud (Amazon EC2):
1.  **Опановано життєвий цикл віртуальних машин Linux:** створено та сконфігуровано інстанс `Linux_DimaLobatenko` на базі ОС Ubuntu Server 24.04 LTS з використанням сучасного апаратного типу `t3.micro`. Завдяки впровадженню скрипта хмарної автоматизації у розділі `User Data` було реалізовано автоматичне розгортання та запуск вебсервера Nginx без необхідності ручного введення команд при першому запуску сервера.
2.  **Засвоєно інструменти мережевого захисту та віддаленого адміністрування:** налаштовано правила брандмауера Security Group для доступу через порти 22 (SSH), 80 (HTTP) та 443 (HTTPS), перевірено роботу вебсервера через публічну адресу Public IPv4, проведено кастомізацію контенту вебсторінки з виведенням складу студентської команди та здійснено аудит активних інстансів за допомогою консольного інтерфейсу AWS CLI.
3.  **Опрацьовано особливості роботи з платформою Windows Server:** виконано запуск інстансу на базі Windows Server 2025 Base, відпрацьовано механізм криптографічної розшифровки пароля локального адміністратора за допомогою закритого ключа `.pem`, встановлено графічне з'єднання за протоколом RDP та здійснено успішне перейменування сервера в налаштуваннях операційної системи на `Windows-Лобатенко_Д`.
4.  **Закріплено кращі практики контролю витрат (FinOps):** після завершення тестування обидва сервери було коректно переведено в стан `Terminated`, що забезпечило своєчасне вивільнення задіяних дискових томів EBS та захистило обліковий запис від непередбачених фінансових нарахувань за межами безкоштовного тарифу AWS Free Tier.
