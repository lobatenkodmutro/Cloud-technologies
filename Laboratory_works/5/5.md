##### Практичне завдання №1. Огляд Storage-as-a-Service

<span>Дайте відповіді на наступні питання:</span>

<span>**1. В чому суть концепції Storage-as-a-Service, коли її доцільно використовувати?**</span>  
Концепція Storage-as-a-Service (STaaS / Сховище як послуга) передбачає надання дискового простору, файлових систем та об'єктних сховищ через мережу Інтернет як керованого хмарного сервісу з оплатою за фактом використання (Pay-as-you-go). Клієнт повністю звільняється від необхідності придбання, проектування та фізичного обслуговування локальних мережевих сховищ (SAN/NAS) і серверів зберігання. Завдання щодо заміни несправних накопичувачів, підтримки відмовостійкості, георезервування та масштабування бере на себе хмарний провайдер. Використовувати STaaS доцільно при високій динаміці зростання даних, для зберігання резервних копій, організації медіа-хостингу, роздачі статики, архівації даних, а також при розробці розподілених хмарних систем, де потрібен безперебійний доступ до даних з будь-якої точки світу.

--------------------------------------------------------------------------------

<span>**2. Наведіть приклади сервісів за моделлю Storage-as-a-Service.**</span>  
У сфері хмарних технологій сервіси STaaS поділяються за архітектурними типами сховищ:
* **Об'єктні сховища (Object Storage):** Amazon S3 (Simple Storage Service), Google Cloud Storage, Microsoft Azure Blob Storage, Backblaze B2, Cloudflare R2.
* **Блокові сховища (Block Storage):** Amazon EBS (Elastic Block Store), Azure Managed Disks, Google Cloud Persistent Disk (підключаються як жорсткі диски до віртуальних машин).
* **Мережеві файлові системи (File Storage):** Amazon EFS (Elastic File System), Amazon FSx, Azure Files, Google Cloud Filestore (спільні файлові папки за протоколами NFS/SMB).
* **Споживчі хмарні диски:** Google Drive, Microsoft OneDrive, Dropbox, pCloud, Mega.

--------------------------------------------------------------------------------

<span>**3. Порівняйте поняття бакету та віртуальної машини на прикладі сервісів від AWS.**</span>  

| Критерій порівняння | Бакет (Amazon S3 Bucket) | Віртуальна машина (Amazon EC2 Instance) |
| :--- | :--- | :--- |
| **Призначення ресурсу** | Логічний контейнер для зберігання неструктурованих об'єктів (файлів). | Повноцінний віртуалізований сервер із виділеними vCPU та RAM. |
| **Рівень абстракції** | Serverless / PaaS (управління інфраструктурою та ОС повністю приховане). | IaaS (повний контроль над гостьовою операційною системою та ПЗ). |
| **Способи доступу** | REST API, HTTP/HTTPS, AWS SDK, AWS CLI, pre-signed URL (без SSH/RDP). | Консольний або графічний віддалений доступ (SSH, RDP, EC2 Instance Connect). |
| **Масштабованість** | Безмежна та автоматична (від декількох байт до петабайт без налаштування). | Обмежена параметрами обраного типу інстансу (потребує Auto Scaling). |
| **Схема тарифікації** | За збережений обсяг ($/GB-місяць) + кількість API-запитів (PUT, GET). | За час роботи процесора ($/годину або $/секунду) незалежно від навантаження. |

<span>**4. Опишіть для чого потрібні такі дії над бакетами як Versioning, Lifecycle та Replication.**</span>  
* **Versioning (Версіонування):** Дозволяє зберігати декілька версій одного об'єкта в одному бакеті. При зміні або видаленні файла попередні версії не знищуються, а зберігаються; видалення створює лише спеціальну мітку Delete Marker. Це захищає від випадкового перезапису, людських помилок та загрози втрати інформації.
* **Lifecycle Management (Правила життєвого циклу):** Автоматизує переміщення об'єктів між різними класами зберігання S3 (наприклад, з S3 Standard до S3 Standard-IA через 30 днів, потім до S3 Glacier через 90 днів) або їх автоматичне остаточне видалення через заданий час. Це суттєво оптимізує фінансові витрати на зберігання даних.
* **Replication (Реплікація):** Автоматична асинхронна передача об'єктів між різними бакетами. Виділяють Cross-Region Replication (CRR) — реплікацію в інший географічний регіон для аварійного відновлення (Disaster Recovery) та зниження затримок для віддалених користувачів, та Same-Region Replication (SRR) — реплікацію в межах того самого регіону (наприклад, між розробницьким та продакшн-акаунтами).

--------------------------------------------------------------------------------

<span>**5. Які методи захисту від несанкціонованого доступу до бакетів існують?**</span>  
1. **S3 Block Public Access:** Централізоване блокування будь-якого публічного доступу до бакета та його вмісту на рівні акаунта чи конкретного сховища.
2. **Bucket Policies:** Декларативні JSON-політики доступу, прикріплені до бакета, які регламентують дозволені/заборонені дії (Actions) для конкретних суб'єктів (Principals), IP-адрес чи умов.
3. **IAM Policies:** Політики доступу на рівні користувачів, груп та ролей AWS IAM.
4. **Access Control Lists (ACLs):** Легасі-система розмежування прав на рівні окремих об'єктів (в сучасній архітектурі рекомендується вимикати на користь Bucket Policies).
5. **Шифрування даних (Encryption):** Шифрування на стороні сервера (SSE-S3, SSE-KMS з управлінням ключами через AWS KMS, SSE-C) та шифрування на стороні клієнта.
6. **S3 Object Lock (WORM — Write Once, Read Many):** Заборона видалення та модифікації об'єктів на встановлений період для відповідності регуляторним вимогам.
7. **Pre-signed URLs:** Тимчасові унікальні посилання з обмеженим часом дії для безпечного завантаження/зчитування файлів авторизованими клієнтами.

##### Практичне завдання №2. Огляд Function-as-a-Service (FaaS)

<span>Дайте відповіді на наступні питання:</span>

<span>**6. В чому суть концепції Function-as-a-Service (FaaS), коли її доцільно використовувати?**</span>  
Суть FaaS (Функція як послуга) полягає в наданні середовища виконання для окремих компактних фрагментів коду (функцій), які запускаються у відповідь на конкретні події (Event-Driven Execution). Розробник пише лише бізнес-логіку функції, а провайдер автоматично виділяє ізольоване середовище, забезпечує миттєве масштабування під потік запитів і гасить ресурси після виконання. Оплата нараховується суворо за мілісекунди фактичної роботи коду та виділену оперативну пам'ять. Використовувати FaaS доцільно для обробки асинхронних подій (завантаження файлів, вебхуки, обробка черг), при фонових або періодичних завданнях (cron-задачі), а також для побудови мікросервісних API з нерівномірним чи спорадичним навантаженням.

--------------------------------------------------------------------------------

<span>**7. Опишіть поняття “Serverless-архітектури”.**</span>  
Serverless (Безсерверна архітектура) — це концепція побудови програмних систем, за якої розробники повністю звільняються від адміністрування фізичних чи віртуальних серверів, операційних систем та контейнерних оркестраторів. Фізична інфраструктура продовжує існувати, але її налаштування, масштабування, моніторинг, оновлення та забезпечення високої доступності повністю делеговані хмарному провайдеру. Головні риси Serverless: відсутність витрат на простоювання (No Idle Cost — -bash у стані спокою), автоматичне горизонтальне масштабування від 0 до тисяч паралельних викликів, подійно-орієнтований характер та інтеграція через заздалегідь налаштовані керовані сервіси.

--------------------------------------------------------------------------------

<span>**8. Порівняйте поняття serverless-архітектури та Function-as-a-Service (FaaS).**</span>  
FaaS є ключовим обчислювальним компонентом (Compute Layer) у складі ширшої концепції Serverless. Поняття *FaaS* стосується безпосередньо виконання програмного коду за подіями (наприклад, AWS Lambda, Azure Functions), тоді як *Serverless-архітектура* охоплює весь стек веб-додатка, включаючи безсерверні сховища (Amazon S3), безсерверні бази даних (Amazon DynamoDB, Aurora Serverless), сервіси обміну повідомленнями (Amazon SQS, SNS) та API-шлюзи (Amazon API Gateway). Таким чином, FaaS — це інструмент виконання коду, а Serverless — це цілісний підхід до побудови системи.

--------------------------------------------------------------------------------

<span>**9. Наведіть приклади serverless-рішень та сервісів Function-as-a-Service (FaaS) у хмарних провайдерів.**</span>  
* **FaaS-сервіси (Обчислення):** AWS Lambda, Google Cloud Functions / Cloud Run, Azure Functions, Cloudflare Workers.
* **Serverless-бази даних та сховища:** Amazon DynamoDB, Amazon Aurora Serverless, Azure Cosmos DB, Google Cloud Firestore, Amazon S3.
* **Serverless-інтеграція та шлюзи:** Amazon API Gateway, AWS Step Functions, Amazon SNS/SQS, EventBridge, Azure Event Grid, Google Cloud Pub/Sub.

##### Практичне завдання №3. Робота з реляційними базами даних в AWS

<span>Дайте відповіді на наступні питання:</span>

<span>**11. Опишіть можливості Amazon RDS (Relational Database Service). До якої хмарної моделі її можна віднести?**</span>   
Amazon RDS являє собою керований хмарний сервіс для автоматизації адміністрування реляційних баз даних. Він бере на себе рутинні завдання: розгортання движка СУБД, інсталяцію оновлень безпеки (Automated Patching), автоматичне резервне копіювання з можливістю відновлення на будь-який момент часу (Point-in-Time Recovery), забезпечення відмовостійкості через дублювання в кількох зонах (Multi-AZ Deployment) та створення копій для читання (Read Replicas). Amazon RDS належить до хмарної моделі **PaaS (Platform as a Service)** або її профільної підкатегорії **DBaaS (Database-as-a-Service)**. Користувач позбавлений доступу до ОС сервера, проте зберігає повний контроль над структурами таблиць, SQL-запитами, індексами та користувачами БД.

--------------------------------------------------------------------------------

<span>**12. Які бази даних підтримує Amazon RDS. Порівняйте їх за можливостями.**</span>  
Amazon RDS підтримує 6 провідних движків реляційних СУБД:
1. **Amazon Aurora:** Власна хмарна реляційна СУБД AWS, повністю сумісна з MySQL та PostgreSQL. Забезпечує до 5 разів вищу продуктивність порівняно зі стандартним MySQL, використовує самовідновлюване розподілене сховище (6 копій у 3 зонах) та підтримує безсерверний режим Aurora Serverless.
2. **PostgreSQL:** Потужна open-source СУБД з чудовою підтримкою складних аналітичних запитів, типів JSON/JSONB, геопросторових розширень (PostGIS) та векторного пошуку.
3. **MySQL:** Найпопулярніша у світі open-source реляційна база даних для веб-проєктів (CMS, електронна комерція), що вирізняється високою швидкістю зчитування.
4. **MariaDB:** Оптимізований відгалужений (fork) двигун від первинних розробників MySQL з розширеною підтримкою продуктивних рушіїв зберігання.
5. **Oracle Database:** Корпоративна комерційна СУБД для важких транзакційних систем (Enterprise OLTP). Підтримує моделі ліцензування BYOL (Bring Your Own License) та License Included.
6. **Microsoft SQL Server:** Корпоративна СУБД від Microsoft з бездоганною інтеграцією в стек .NET та інфраструктуру Windows.

--------------------------------------------------------------------------------

<span>**13. Порівняйте процес розгортання БД на базі Amazon RDS (PaaS-модель) та EC2 + MySQL (або інша БД) вручну (IaaS-модель). Коли доцільно використовувати їх?**</span>  

| Критерій | Amazon RDS (PaaS / DBaaS) | Self-Hosted на Amazon EC2 (IaaS) |
| :--- | :--- | :--- |
| **Швидкість розгортання** | 5–10 хвилин через графічну консоль або виклик API. | Кілька годин (створення ВМ, оновлення ОС, встановлення та конфігурація СУБД). |
| **Адміністрування та патчі** | Автоматичне оновлення ОС та движка у вибрані вікна обслуговування. | Ручне встановлення оновлень та патчів безпеки системним адміністратором. |
| **Резервне копіювання** | Автоматичні щоденні знімки та відновлення Point-in-Time. | Потрібно самостійно писати скрипти дампів та конфігурувати їх передачу на S3. |
| **Висока доступність (HA)** | Вмикається одним прапорцем (Multi-AZ із автоматичним failover). | Складне ручне налаштування реплікації, керованих IP та Heartbeat-скриптів. |
| **Доступ до ОС хоста** | Повністю заблокований (немає SSH/RDP до фізичного сервера). | Повний Root/Administrator доступ до конфігураційних файлів та файлової системи. |
| **Сфера застосування** | Стандартні проєкти, де важлива швидкість розробки та стабільність. | Необхідність кастомних плагінів СУБД, нестандартних параметрів ОС або ліцензій. |

--------------------------------------------------------------------------------

<span>**14. Опишіть для чого потрібні операції масштабування, створення снепшотів, моніторингу та логування баз даних.**</span>  
* **Масштабування (Scaling):** Забезпечує адаптацію бази даних до зростаючого навантаження. *Вертикальне масштабування* (Scaling Up) збільшує ресурси vCPU/RAM та обсяг диска одного сервера; *горизонтальне масштабування* (Scaling Out) створює Read Replicas (копії лише для читання) для зняття навантаження з майстер-вузла.
* **Створення снепшотів (DB Snapshots):** Створення точкових резервних копій усього екземпляра бази даних у сховищі S3. Необхідно для відновлення системи перед внесенням критичних змін у схему даних чи оновленням релізу.
* **Моніторинг (Monitoring):** Відстеження ключових системних метрик (CPU Utilization, Freeable Memory, Read/Write IOPS, Database Connections) за допомогою Amazon CloudWatch для своєчасного виявлення вузьких місць у продуктивності.
* **Логування (Logging):** Запис журналів помилок (Error Logs) та повільних запитів (Slow Query Logs) для аналізу проблемних SQL-запитів, їхньої подальшої оптимізації та розслідування інцидентів безпеки.

<span>**15. Порівняйте поняття реляційних та NoSQL баз даних. Чи підтримує NoSQL сервіс Amazon RDS?**</span>  
Реляційні бази даних (SQL) зберігають інформацію у строго структурованих таблицях із чітко визначеною схемою (Schema-on-Write), підтримують зв'язки між таблицями та гарантують транзакційну цілісність за стандартом ACID (Atomicity, Consistency, Isolation, Durability). Натомість NoSQL-бази даних є нереляційними сховищами з гнучкою динамічною схемою (Schema-on-Read), які оптимізовані під горизонтальне масштабування, обробку гігантських масивів неструктурованих даних та досягнення ультранизької затримки читання/запису. Сервіс Amazon RDS розроблений **виключно для реляційних баз даних** і NoSQL не підтримує. Для NoSQL-рішень в екосистемі AWS передбачено окремі спеціалізовані сервіси: Amazon DynamoDB, Amazon DocumentDB та Amazon Keyspaces.

<span>**16. Наведіть класифікацію сучасних NoSQL баз даних. Де вони використовуються в хмарних технологіях?**</span>  
1. **Ключ-значення (Key-Value):** Найдрібніша та найшвидша модель, де дані зберігаються у вигляді пар унікального ключа та значення. Приклади: *Amazon DynamoDB, Redis, Memcached*. (Використання: сесії користувачів, кешування, кошики покупок).
2. **Документні (Document Stores):** Дані зберігаються у вигляді ієрархічних JSON/BSON документів. Приклади: *Amazon DocumentDB, MongoDB, Couchbase*. (Використання: каталоги товарів з мінливими атрибутами, системи CMS, профілі користувачів).
3. **Колонкові (Wide-Column Stores):** Дані організовані в родини колонок, що оптимізовано під миттєвий запис часових рядів. Приклади: *Amazon Keyspaces, Apache Cassandra, HBase*. (Використання: IoT-телеметрія, логи подій, аналітика фінансових транзакцій).
4. **Графові (Graph Databases):** Дані представлені у вигляді вузлів та ребер для відображення складних зв'язків. Приклади: *Amazon Neptune, Neo4j*. (Використання: соціальні графи, рекомендаційні рушії, виявлення мережевих зв'язків).

<span>**17. Опишіть можливості та застосування Amazon DynamoDB.**</span>  
Amazon DynamoDB — це повністю керована безсерверна NoSQL база даних класифікації Key-Value та Document, що забезпечує стабільну затримку в кілька мілісекунд при будь-якому обсязі даних. Її можливості включають автоматичне партиціювання даних, підтримку режиму On-Demand (автомасштабування під трафік) та Provisioned (фіксовані ресурси), автоматичне очищення застарілих даних за таймером TTL (Time to Live), вбудовану реплікацію між 3 зонами доступності та підтримку Global Tables для мультирегіонального запису. Застосовується в мобільних іграх (збереження стану та лідерборди), e-commerce (кошики та профілі), фінансових транзакціях та мікросервісних бекендах.

<span>**18. Опишіть основні поняття Amazon DynamoDB: Primary Key, WCU та RCU.**</span>  
* **Primary Key (Первинний ключ):** Унікально ідентифікує кожен елемент (Item) у таблиці. Буває двох типів:
  - *Partition Key (Simple Key):* Одноатрибутний ключ, значення якого хешується для визначення фізичної партиції зберігання.
  - *Composite Primary Key (Partition Key + Sort Key):* Складений ключ, де Partition Key визначає партицію, а Sort Key впорядковує елементи всередині неї.
* **RCU (Read Capacity Unit):** Одиниця пропускної здатності читання. 1 RCU надає можливість здійснити 1 суворо узгоджене читання (Strongly Consistent Read) або 2 узгоджених у кінцевому підсумку читання (Eventually Consistent Read) на секунду для елемента розміром до 4 КБ.
* **WCU (Write Capacity Unit):** Одиниця пропускної здатності запису. 1 WCU надає можливість виконати 1 запис на секунду для елемента розміром до 1 КБ.

<span>**19. Порівняйте сервіси AWS для роботи з NoSQL базами даних - Amazon DynamoDB, Amazon DocumentDB та Amazon Keyspaces**</span>  

| Критерій порівняння | Amazon DynamoDB | Amazon DocumentDB | Amazon Keyspaces |
| :--- | :--- | :--- | :--- |
| **Модель даних** | Key-Value та Document. | Документна (Document / BSON). | Колонкова (Wide-Column). |
| **Сумісність з API** | Власний пропрієтарний API AWS. | Повна сумісність з MongoDB API. | Повна сумісність з Apache Cassandra (CQL). |
| **Архітектурний тип** | Повністю безсерверна (Serverless). | Кластерна (екземпляри ВМ + розподілене сховище). | Повністю безсерверна (Serverless Cassandra). |
| **Управління ресурсами** | Автоматичний режим On-Demand або RCU/WCU. | Вертикальне масштабування інстансів та Read Replicas. | Автоматичне On-Demand виділення місткості. |
| **Типові сценарії** | Високонавантажені веб/мобільні сервіси, ігри. | Проста міграція існуючих MongoDB-додатків у хмару. | Обробка велетенських потоків телеметрії IoT та логів. |

<span>**20. Наведіть приклади ІТ-задач, де буде доцільно використовувати Amazon DynamoDB, Amazon DocumentDB та Amazon Keyspaces. Як їх розгорнути в AWS?**</span>  
* **Amazon DynamoDB:**
  - *Задача:* Збереження історії тренувань та логів активності користувачів фітнес-додатка FitPulse.
  - *Порядок розгортання:* Перейти у веб-консоль DynamoDB -> натиснути **Create table** -> ввести назву UserActivity -> вказати Partition Key user_id (String) та Sort Key timestamp (Number) -> обрати режим On-Demand -> натиснути **Create table**.
* **Amazon DocumentDB:**
  - *Задача:* Централізований каталог товарів маркетплейсу з мінливими характеристиками (одяг, побутова техніка, автозапчастини), який переноситься з локального MongoDB.
  - *Порядок розгортання:* Перейти у сервіс DocumentDB -> натиснути **Create cluster** -> обрати конфігурацію інстансів (наприклад, db.t3.medium) -> ввести ідентифікатор кластера й пароль адміністратора -> налаштувати мережеві параметри VPC та Security Group -> підключитися з коду.
* **Amazon Keyspaces:**
  - *Задача:* Прийом та збереження високочастотної телеметрії (показники температури, тиску, вібрацій) від десятків тисяч промислових датчиків.
  - *Порядок розгортання:* Перейти у сервіс Amazon Keyspaces -> створити Keyspace IndustryIoT -> всередині простору натиснути **Create table** -> описати структуру колонок за допомогою синтаксису Cassandra Query Language (CQL) та зберегти.

##### Висновки
У ході виконання лабораторної роботи №5 було детально досліджено спеціалізовані сервіси та архітектурні компоненти хмарного провайдера Amazon Web Services (AWS). Під час практичного аналізу було опановано концепцію Storage-as-a-Service (STaaS) на прикладі об'єктного сховища Amazon S3, вивчено механізми забезпечення безпеки (Bucket Policies, S3 Block Public Access), версіонування та автоматизацію життєвого циклу об'єктів (Lifecycle Rules). Опрацьовано парадигму безсерверних обчислень Function-as-a-Service (FaaS) та можливості сервісу AWS Lambda для побудови подійно-орієнтованих архітектур (Event-Driven Architecture). Крім того, виконано комплексне порівняння керованих реляційних баз даних у середовищі Amazon RDS (PaaS / DBaaS) та нереляційних NoSQL-рішень (Amazon DynamoDB, DocumentDB, Keyspaces), задокументовано методи їхнього масштабування та наведено практичні алгоритми розгортання для вирішення реальних завдань у галузях E-Commerce, FinTech, GameDev, IoT та штучного інтелекту.
